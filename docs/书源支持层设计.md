# 轻阅 Lite · 书源支持层设计文档

> 范围：**App 侧如何「支持书源」** —— 从导入到运行到诊断的完整契约。
> 引擎侧（柴阅/Chaiyue）只作为**契约的实现方**出现，不在本文展开。
> 配套：`docs/移植-柴阅引擎.md`（引擎换装）、`NovelHub聚合小说-书源设计文档.md`（一个真实书源的实例）。

---

## 0. 设计目标

一个书源要在 App 里「能用」，必须满足 **7 条契约**。本文把它们逐条写清楚，
每条都附**为什么**（都是踩过的坑）与**怎么验**。

| # | 契约 | 一句话 |
|---|---|---|
| **A** | **发现页** | `exploreUrl` ⇒ 分类 + 筛选栏；筛选要能**改变量**并**立即生效** |
| **B** | **搜索** | `searchUrl` + `ruleSearch` |
| **C** | **详情/目录/正文** | `ruleBookInfo` / `ruleToc` / `ruleContent` |
| **D** | **登录** | `loginUi` / `loginUrl` / `loginCheckJs` + 整源解锁 + 浏览器 |
| **E** | **变量与状态** | **三套槽**各管各的；改变量 ⇒ **缓存必须失效** ⭐⭐⭐ |
| **F** | **诊断与定责** | 出问题时**能一次分清是书源、引擎还是宿主** ⭐⭐⭐ |
| **G** | **能力与降级** | 书源先探测再调用；宿主提供能力并**让用户能把探测结果贴回来** |

---

## 1. 书源的生命周期

```
导入/粘贴 JSON
   └─ 校验（必需字段 + 规则形态）        ← 失败要**说清缺什么**
      └─ 归一化（App 侧模型 ⇄ 引擎侧模型）
         └─ 运行（op 分派：search / exploreKinds / explore / bookInfo / toc / content / login / …）
            └─ 状态落盘（三个槽）
               └─ 诊断（不可信原因 / 能力探测 / 决定性诊断）
```

⭐⭐⭐ **设计原则**：**每一层都要能单独说清「我干了什么、为什么不行」** ——
静默失效（不报错、只是空）是最坏的一种，因为它让用户和开发者都无从下手。

## 2. 数据模型

### 2.1 App 侧模型 vs 引擎侧模型

| 层 | 模型 | 谁负责 |
|---|---|---|
| App 侧 | `BookSource`（`Core/BookSource.swift`）| 导入、存储、UI 展示 |
| 引擎侧 | `LegadoEngineHost.Source` = 柴阅的 `BookSource` | 运行 |

⇒ **映射靠 JSON 直解**（两边字段名同 Legado）⇒ 不做逐字段手写转换 ⇒ ⇒ 只保留一份转换代码。

⚠️ **未知字段要能扛住**：引擎侧用 `AnyCodingKey` + `extras` ⇒ 站方写的自定义字段不丢。

### 2.2 宿主的类型门面（`LegadoEngineHost`）

```swift
public enum LegadoEngineHost {
    public typealias Source        = ChaiyueModels.BookSource
    public typealias BookModel     = ChaiyueModels.Book
    public typealias ChapterModel  = ChaiyueModels.BookChapter
    public typealias SearchResult  = ChaiyueModels.SearchBook
    public typealias Kind          = ChaiyueModels.ExploreKind
    public typealias Vars          = [String: String]
    public typealias WebBook       = ChaiyueEngine.WebBook
    public typealias Environment   = ChaiyueEngine.SourceEnvironment
    public typealias Store         = ChaiyueEngine.KeyValueStore
}
```

⭐⭐⭐ **两条硬规矩**（都是 CI 报过错）：

1. **宿主只 `import LegadoEngine`** ⇒ 柴阅的类型**必须**走 `LegadoEngineHost.` 别名
   （Swift 的 `import` **不 re-export** ⇒ 直接写 `ChaiyueEngine.X` 编译不过）
   ⇒ **静态门禁**扫「宿主源码里出现 `ChaiyueEngine.` / `ChaiyueModels.` / 裸用柴阅类型名」⭐⭐⭐
2. **同名问题**：模块名 `LegadoEngine` 与引擎门面 enum 同名 ⇒ 宿主侧一律用 `LegadoEngineHost.X`

## 3. 契约 A：发现页 ⭐⭐⭐

### 3.1 输入输出

**输入**：`source.exploreUrl`（可以是静态数组，也可以是 `@js:` / `<js>` 薄壳）

**输出**（App 内部 DTO）：

```swift
struct KindsDTO { var kinds: [KindDTO] = []; var filters: [FilterDTO] = []; var error: String? }
struct KindDTO   { var title, url, style, group: String }
struct FilterDTO { var title, type, `default`, paramKey, action: String; var chars: [String] }
```

### 3.2 kinds ↔ filters 的划分（**唯一容易错的地方**）

站方返回的每一项可能是**分类**也可能是**筛选栏**，判据**只看 `type`**：

| 站方返回 | 判定 | 去处 |
|---|---|---|
| `type` 缺省或 `"url"`，且 `url` 非空 | 分类 | `kinds` |
| `type` 缺省或 `"url"`，且 `url` **为空** | **组标题**（装饰行）| 只更新后续项的 `group` |
| `type` != `"url"`（`select`/`toggle`/`button`）| **筛选栏** | `filters` |

⚠️⭐⭐⭐ **顺序必须是「先看 type，再判组标题」** ——
否则「`url` 为空但 `type:"select"`」的筛选项会被当组标题**扔掉** ⇒ **那个源就没有筛选栏了**
⇒ **这条必须钉门禁**（`explore-diag-attribution` 里有专门的变异）⭐⭐⭐

### 3.3 筛选动作的通用链路

```
用户点筛选项
   ├─ paramKey 非空 ⇒ App 写「源级变量」
   └─ paramKey 为空 ⇒ App 执行站方 action
                    ↓
         站方 action 读 infoMap['<标题>']  ⇒ 写 source.setVariable ⇒ java.refreshExplore()
                    ↓
         App 重跑 exploreKinds（refresh）⇒ 重跑 explore（书籍列表）
```

⭐⭐⭐ **App 侧铁律**：

1. **优先执行站方 action**（站方自己知道该写哪个键 ⇒ **通用**）
   ⇒ 失败/无 action 才落「App 自己写 paramKey」
2. **paramKey 的键名 ≠ 筛选标题** ⇒ App **不能猜键名** ⇒ ⇒ 兜底时也要**从 action 里解析**
3. **App 必须注入 `infoMap`**（站方 action 全靠它取用户选的值）
4. **执行 action 后必须让缓存失效**（否则「改了没反应」）

### 3.4 `paramKey` 的来源与坑

`paramKey` = 「App 该写哪个源级变量」⇒ 从站方 action 里解析：

| action 形态 | 解析结果 |
|---|---|
| `show(infoMap['平台'],'find_source')` | `find_source`（第二个引号参数）|
| `c['src']=v; c['find_source']=String(v);` | `src`（第一个赋值）—— ⚠️ 但 `src` 对缓存键不合适 ⇒ 见 §5.3 |

⚠️ **解析不出来 ⇒ 空 ⇒ 走「执行 action」那条路** ⇒ 这也是「通用」的关键。

## 4. 契约 B/C：搜索、详情、目录、正文

| 契约 | 要点 |
|---|---|
| **B 搜索** | `searchUrl` 可 `@js:`；`ruleSearch.bookList` 可 `@js:`；结果要能翻页 |
| **C1 详情** | `ruleBookInfo.*` 各自独立求值（作者/封面/分类/最新章/字数/目录 URL 各一条）⇒ ⇒ **`@js:` 薄壳要各自独立**（不能共用一个上下文）|
| **C2 目录** | `ruleToc.chapterList` + `chapterUrl`；⚠️ `chapterUrl` 为空 ⇒ 章节被丢 |
| **C3 正文** | `ruleContent.content`；⚠️ `useWebView` ⇒ 走引擎的后台 WebView 渲染（宿主提供 delegate）|

⚠️⭐⭐⭐ **薄壳的统一形态**（宿主单条规则上限 ~8192 ⇒ 大段 JS 放不进规则字段）：

```js
@js:
var __out = nhSlim_nh_ruleToc_chapterList.call(this,
  (typeof result !== 'undefined') ? result : '',
  (typeof book   !== 'undefined') ? book   : {},
  (typeof page   !== 'undefined') ? page   : 1);
return __out;
```
⇒ **所有宿主变量都要 `typeof` 兜底**（宿主不保证给全）⇒ 缺了也不炸。

⚠️ **正文里的 `useWebView`** ⇒ 宿主必须实现引擎的 `SourceUIDelegate.renderWebView` ⇒
⇒ 否则**静默失败**（正文空但不报错）⇒ **这条要进能力探测表**。

## 5. 契约 E：变量与状态 ⭐⭐⭐（全书源最容易出事的地方）

### 5.1 三套槽，各管各的

| 槽 | 引擎 API | 语义 | 谁写 | 谁读 |
|---|---|---|---|---|
| **① 书源变量** | `source.get/put(k,v)` | 键值 map | 站方脚本、App | 站方脚本 |
| **② 站方变量** | `source.getVariable()/setVariable(str)` | **一整串**（通常是 JSON）| 站方脚本（筛选 action、菜单切台）| 站方脚本（explore/search 出口）|
| **③ 登录信息** | `source.getLoginInfoMap()/putLoginInfo` | 表单数据 | 登录面板 | 登录流程 |

⚠️⭐⭐⭐ **混用会造成极隐蔽的 bug**：书源把令牌写进 ② ⇒ 把平台/筛选状态冲掉（症状：**登录一次发现页筛选被重置**）。

⇒ **App 侧的义务**：三套槽**物理隔离**（不同存储键、不同读写入口、不同截断策略）。

### 5.2 App 侧的实现

| 槽 | App 存储 | 备注 |
|---|---|---|
| ① | `sourcevars.<源URL>`（一个 JSON map 串）| 8K 上限保护 |
| ② | `sourcevariable.<源URL>`（一整串）| 8K 上限保护 |
| ③ | `sourcelogin.<源URL>`（明文 JSON）| 引擎侧加密 ⇒ **存取时转换** |

⚠️ **8K 上限**：变量是**回流**的（引擎回传 ⇒ 存成用户变量 ⇒ 下次再喂回去）⇒
手滑存一次大文本 ⇒ **永久撑大** ⇒ 登录面板排版炸 ⇒ watchdog 杀进程 ⇒ ⇒ **超长一律拒收**。

### 5.3 缓存失效约定 ⭐⭐⭐

| 机制 | 做法 | 谁负责 |
|---|---|---|
| **变量进缓存键** | 让「变化的量」进键 | 双方约定键的组成 |
| **epoch 作废** | 时间戳顶到现在 | 书源侧（`nhCyjTocEpoch` 等）|
| **显式清空** | 改完变量顺手清缓存项 | 书源侧（`nhCyjCats`/`nhMyMenu`）|
| **筛选后清缓存** | App 侧 | **App 侧必须做** ⭐⭐⭐ |

⚠️⭐⭐⭐ **「切台没反应」的经典案例**（宿主与书源**各修一半**才对）：

| 侧 | 问题 | 解法 |
|---|---|---|
| 书源 | 只改站方变量的 `src`，而宿主缓存键含 `find_source` ⇒ 键不变 ⇒ 命中缓存 | 同时写 `find_source`/`find_tab` |
| 宿主 | 缓存键只读书源变量槽，看不到站方变量 ⇒ 键也不变 | 缓存键**同时读站方变量槽** + 筛选后**清缓存** |

⇒ **只做一侧仍会「点了没反应」** ⭐⭐⭐

## 6. 契约 D：登录 ⭐⭐⭐

### 6.1 三种登录

| 形态 | 机制 | App 的义务 |
|---|---|---|
| **表单登录** | `loginUi`（字段/按钮）+ `loginUrl`（执行）| 渲染条目、传 `formValues`、执行 action |
| **登录态探测** | `loginCheckJs` | 执行并把结果翻译成人话 |
| **整源解锁** | 站方 `nhAuth()` 门禁 + 口令 | 提供「解锁整个源」入口；⚠️ **不自动绕过** |

⚠️⭐⭐⭐ **整源解锁的立场**：站方门禁的目的是「**源不外传**」⇒
⇒ App **不自动填、不自动解锁** ⇒ 只提供入口 + 明确提示 ⇒ **这是合规边界，不是功能缺失**。

### 6.2 登录面板的「行」从哪来

⚠️⭐⭐⭐ **必须支持 `@js:` 的 `loginUi`** ——
站方常把登录菜单写成薄壳（正文在 `jsLib`）⇒ 只解析静态 JSON ⇒ **面板空白、一个按钮都没有** ⇒
⇒ **用引擎的 `resolveLoginRows`**（它会先跑 `loginJs`、再求值 `loginUi`）⭐⭐⭐

⚠️ **静态优先**：引擎的 `resolveLoginRows` **只处理 `@js:`/`<js>`**；静态 JSON 走引擎的**预设行** ⇒
⇒ **静态源不能被预设行顶掉** ⇒ 规则：**静态为空时才用引擎求值出来的**。

### 6.3 浏览器与验证码（登录的配套设施）

引擎把这些交给宿主（`SourceUIDelegate`）：**渲染 / 浏览器 / 验证码 / toast / 复制 / 外链 / 视频**。

⇒⭐⭐⭐ **App 必须逐条实现**（少一个就是一类功能**静默失效**）⇒
⇒ **要主动对拍清单**，不能等用户报 ⭐⭐⭐

| 引擎能力 | App 侧实现 |
|---|---|
| `renderWebView` | 后台 WKWebView 渲染（正文的 `useWebView`）|
| `startBrowser` / `startBrowserAwait` | **内嵌浏览器**（不是系统 Safari！⇒ 否则 Cookie 读不回来 ⇒ 登录永远失败）|
| `showBrowser` | 浮层浏览器 |
| `verificationCode` | 验证码输入 |
| `toast` / `copyText` / `openURL` / `openVideoPlayer` | 各自的系统能力 |

⚠️ **内嵌浏览器的铁律**（书源源码原话）：
> 「跳 Safari 的话，登录后的 cookie 落在 Safari 的罐里，**我们读不回来** ⇒ 番茄的 token 就永远拿不到 ⇒ 番茄的书依然读不了。」

## 7. 契约 F：诊断与定责 ⭐⭐⭐

### 7.1 三层定责

出问题时必须能分清：

| 层 | 判据 | 例子 |
|---|---|---|
| **书源侧** | 站方接口给了空/错误内容；规则与站方现状不匹配 | 「站方返回空内容」/「站方有内容但规则未匹配」|
| **引擎侧** | 引擎解析链内部出错 | 规则求值抛错、URL 构造失败 |
| **宿主侧** | 宿主接线/状态/缓存问题 | 「站方给了筛选项，但适配层丢了」|

⚠️⭐⭐⭐ **判定必须靠【同一次请求的事实】**，不能靠推理：
- 状态码 / 响应字节 / 最终 URL / 规则形态 / 解析出几本 / **判定结论**
⇒ 这套字段由**引擎在同一次请求里**带回 ⇒ 宿主回传 ⇒ UI 显示 ⇒ **一次定责** ⭐⭐⭐

### 7.2 「不可信」提示必须带原因

❌ 「书单 0 本」 ⇒ 用户只能来问「谁的锅」
✅ 「书单 0 本（站方有内容 12480 字节，但书的解析规则没匹配上 ⇒ **书源规则过时**）」

⇒ **每条「不可信」提示都要能展开成三种可能之一** ⭐⭐⭐

### 7.3 能力探测（书源侧）+ 贴回机制

书源探测宿主缺什么 ⇒ 写进书源变量 + `java.log('[NH-CAPS] …')` ⇒
⇒ **用户搜 `NH-CAPS` 就能贴回来** ⇒ 第二轮对症适配 ⭐⭐⭐

App 侧的对应义务：**引擎日志面板必须能复制** ⇒ 否则用户拿不到这段证据。

### 7.4 日志纪律

- ⭐⭐⭐ **只打键名与长度，不打值**（变量里有 token/密码）
- ⭐⭐⭐ **打最终值，不打中间值**（中间值会误导）
- ⭐⭐⭐ **诊断输出里不许混入「和症状长得像的内容**（否则无法归因）

## 8. 契约 G：能力与降级

| 谁 | 义务 |
|---|---|
| **书源** | 每个宿主 API **先探测再调用**，缺了降级，**绝不抛 `ReferenceError`**；顶层符号带前缀（jsLib 是间接 eval ⇒ 顶层进全局 ⇒ 撞名污染别的书源）|
| **App** | 提供能力；**主动**把「我缺什么」暴露给用户；不要让缺能力变成静默失败 |

⚠️ App 侧也要声明自己的**最小能力集**（例如：是否支持 `useWebView`、是否内嵌浏览器、是否求值 `@js:` 的 `loginUi`）⇒
⇒ 书源可以据此降级 ⇒ 而 App 变更能力时**书源侧不用改** ⭐⭐⭐

---

## 9. 与引擎的关系

- App **只走引擎的 public API**（`WebBook` / `SourceEnvironment` / `KeyValueStore`）⇒ 不碰引擎内部
- App 提供 `KeyValueStore` 的实现 ⇒ **引擎的状态由 App 持久化** ⇒ 跨会话自动保持
- App 实现引擎要求的界面协议（`SourceUIDelegate` / `SourceInteractionPresenter`）⇒ 登录配套设施才活
- 引擎换装时（自研 → 柴阅）⇒ **App 的契约不变**，只换实现 ⇒ ⇒ 这就是契约化的价值 ⭐⭐⭐

---

## 10. 宿主差异 ⇒ 源侧适配 vs App 侧适配

⭐⭐⭐ **判据：谁掌握事实，谁改。**

| 情形 | 该谁改 | 例子 |
|---|---|---|
| 宿主缺某个引擎能力 | **App 侧**（补实现）| 缺内嵌浏览器 ⇒ App 实现 `startBrowser` |
| 宿主缓存键与变量不同步 | **双方都改**（书源同步写键 + App 清缓存）| 切台没反应 |
| 宿主不求值 `@js:` 的 `loginUi` | **App 侧**（改用引擎求值）| 登录面板没按钮 |
| 站方某平台源站挂了 | **书源侧**（标注实测状态）| 部分分类没法实测 |
| 站方规则与现状不匹配 | **书源侧**（更新规则）| 「有内容但规则未匹配」|

⇒ **App 侧适配**必须**尽量写成宿主无关的形式**（依赖「约定」而不是「实现」）⇒ ⇒ 换宿主时同一份源仍可用 ⭐⭐⭐

## 11. 门禁体系（契约都要有牙齿）

| 门禁 | 钉住的契约 |
|---|---|
| `chaiyue-port-contract` | 宿主走引擎 public API、不回传变量、两套语义、无初始化循环 |
| `filter-action-wiring` / `filter-var-roundtrip` | 筛选通用性（优先 action、键名从 action 解析）+ **真跑**「写入 ⇒ 站方读回」 |
| `explore-diag-attribution` | 「0 本」能定责（书源 / 引擎 / 宿主）+ 适配层判定顺序 |
| `login-rows-wiring` / `login-platform-wiring` | 登录行能求值 + 配套设施（浏览器/验证码/渲染）真的接上 |
| `conditional-import-gate` | 条件编译块的 import 完整性（抓 Apple-only 的「cannot find X」）|
| `app-type-sanity` | 同名/嵌套类型作用域（宿主不能裸用柴阅类型名）|
| `linux-compile-gate` + `swift 原生层` | 宿主与引擎在沙盒里真编译真跑 |

⭐⭐⭐ **门禁纪律**（每条都适用）：
1. 每条断言都要问「**把实现改坏，它会不会红**」⇒ **真变异**（改文件 ⇒ 跑 ⇒ 必须红）
2. 变异锚点必须**跟着实现走**（代码一改锚点要改）
3. `String.replace` **不带 g 只换第一处** ⇒ 多处改动要用 `split/join` ⭐⭐⭐
4. 断言前先**剥注释**（注释里写「不要 xxx」会误判）
5. **沙盒编不到的代码**（UIKit/WebKit）⇒ 必须有**静态门禁**兜底 ⭐⭐⭐

## 12. 已知缺口

| 缺口 | 影响 | 计划 |
|---|---|---|
| 宿主能力的**最小能力集**还没对外声明 | 书源无法按宿主能力降级 | App 侧加一个能力清单 API |
| 诊断目前是**逐 op**的（explore/exploreKinds 各一套）| 其它 op 还没定责 | 抽成统一的诊断信封 |
| 书源侧的**自检**（§15 清单）靠人工 | 出包前易漏 | 做成 CI 步骤（用真源跑）|
| 跨宿主兼容只验过轻阅 + 柴阅 | 别的宿主未验 | 保留「宿主无关写法」约定 |

## 13. 演进规则

1. ⭐⭐⭐ **契约只加不改**：破坏性变更要新版本号，且书源侧能同时兼容新旧
2. ⭐⭐⭐ **诊断字段向后兼容**：老版本 App 读到新字段要能忽略
3. ⭐⭐⭐ **能力探测表是公开契约**：加能力 ⇒ 加表项 + 文档
4. ⭐⭐⭐ **每次踩坑都要沉淀成门禁**（而不是只写进提交信息）—— 这几轮的真实教训
