# 全量替换成「阅读2.0（YueduReader）引擎」的架构结论（2026-11-10）

证据：`/workspace/work/refipa/app/Payload/YueduReader.app`（IPA 解包）
- 主二进制 `YueduReader`（68MB，Swift 原生；Flutter/Firebase 只是其中一部分）
- 资源 `ruleEngine.js`（52KB）
- Swift 源文件路径残留在二进制里（530 个 `yuedu_app/*.swift`）

## 1. ⭐ 他的引擎不是「纯 JS」，而是三层
```
Swift 宿主 (yuedu_app/ModernRuleEngine.swift)
 ├─ 规则解析/拆解：RuleAnalyzer / RegexExtractor / <js>…</js>|@js:… 拆分
 ├─ 取值分派：extractors（content/baseUrl/redirectUrl/isJSON/isRegex/nextChapterUrl）
 ├─ jsEvaluator → LegadoHeadlessWebView（WKWebView）里跑站方 JS
 ├─ LegadoJSBridge.swift：宿主 API（java.* / source.* / cookie.* / cache.*）
 │    + js.network transport（站方 ajax 走 JS 侧发起，宿主只做 transport）
 ├─ stringRuleCache（规则字符串缓存）· debugObserver（诊断观察者）· engineGen（引擎代，缓存失效用）
 └─ ruleEngine.js（WKWebView 内的取值层：CSS/XPath/JSONPath/regex 统一取值）
```
二进制里的关键日志串（直接可查）：
- `stage=jsLib.evaluated jsLibLen=%d engineGen=%llu jsError=%@` ⇒ **jsLib 支持，且有 jsError 捕获**
- `stage=js.network path=%@ status=%d timedOut=%@ bodyLen=%d bodyHead=%@` ⇒ **站方 ajax 在 JS 侧发起**
- `⟐ ajax without a transport` ⇒ ajax 必须有 transport
- `stage=variable.put key=… value=…` / `variable.get` ⇒ 站方变量读写有分阶段标记
- `⟐ rule JS error` / `ModernRuleEngine extraction failed (rule: …)` / `unsupported rule syntax: …`

## 2. ⭐⭐⭐ 与「上一窗口我说的」一处更正
上一窗口我说「他们不支持 jsLib/eval 型规则」——**错**。
错因：只看了 `ruleEngine.js` 这一个 JS 文件；**拆 `@js:`/`<js>` 与 jsLib 装载都在 Swift 侧**（ModernRuleEngine.swift）。

## 3. ⭐ 版权边界（必须先定，否则方向就是错的）
- `ruleEngine.js` 是**他的源码**，从 IPA 提取后搬进轻阅 = **直接复制他人代码 ⇒ 侵权**。
- 他的 App **闭源**（搜到的 GitHub 仓库都是安卓「阅读/Legado」的书源分享，不是这个 iOS App）。
- ⇒ **可做**：学他的**架构与设计**（分层 / stage 诊断 / engineGen / stringRuleCache / debugObserver / js.network transport）
- ⇒ **可做**：拿他的 `ruleEngine.js` 当**能力清单与对照实现**（它支持哪些取值模式），**自己实现**缺的
- ⇒ **不做**：把 `ruleEngine.js` 原文拷进轻阅产物

## 4. 「全量替换」在轻阅的**真实落点**
轻阅现状：自研 Swift 引擎（legado-engine）+ App 侧 WKWebView 求值器（`Engine/WebViewJSExecutor.swift`）。
「换成他的引擎」= **把引擎层搬回 WKWebView 架构**（= 我们 2026-10-25 退役的那套），并按他的分层重做。

⭐ **好消息：原料我们都有**
- `QiReaderLite/Resources/engine/` 里现成的 11 个 JS 资源：engine.js / jsonpath.js / jsoup-compat.js /
  org-jsoup.js / sextant-filter.js / packages-native.js / packages_stub.js / java-api.js / source-api.js / sha1.js
- `Core/RuleSandbox.swift`（WKWebView 壳 + `__qrInvoke` + prompt 同步通道）**还在**，没删
⇒ 替换不是从零写，是**把接回来的通路按他的架构升级**。

## 5. ⚠️ 影响面与风险（必须说清）
1. **legado-engine 作废**：用户另一个窗口在自研它 ⇒ 轻阅全量替换 = 与它脱钩（不主动改它，只是不再用）。
2. **已验证的东西会作废**：自研 Swift 引擎已过 2258 项门禁 + 多轮真机；替换后要重新过一遍。
3. **老坑会回来**（2026-10-25 踩过）：主线程 prompt 自等死锁（build273 闪退）、站方 JS 被跑 2~3 次⇒
   `java.ajax` 重复发⇒限流打爆（番茄 3 次/天）、jsLib 与宿主注入顺序（覆盖 → 403 无效JWT）。
4. **工作量**：多周级（规则引擎主体 + JS 取值层 + 宿主桥 + 接线 + 门禁 + 真机对拍）。

## 6. ⭐ 落地顺序（我自定的纪律：替换期间**必须留回退**，否则一旦新引擎跑不通用户会同时失去两个能用的）
- **阶段 1｜双引擎并存**：恢复「新引擎 ↔ WKWebView 引擎」双通路接线（`SourceService.invokeEngine` 那层），
  按他的分层补 stage 诊断 / engineGen / stringRuleCache；用真实源逐 op 对拍。
- **阶段 2｜取值层能力对账**：以他的 `ruleEngine.js` 为**清单**（不是代码），逐条对照我们的 jsonpath/sextant/jsoup
  ⇒ 缺的自己实现 ⇒ 出**能力差集**清单。
- **阶段 3｜主链路切换**：主链路走 WKWebView 引擎；自研 Swift 引擎降为对照/回退；全绿后再物理退役。

## 7. 与本轮已交付的 build286 的关系（不冲突）
build286 修的是**宿主桥接层**（`JSON.stringify((0,eval)(…))` ⇒ undefined ⇒ 完成值不可桥接 ⇒ WebKit code 5），
并顺带把「完成值恒为字符串 + 带回 typeof」做成**任何后端都能用的契约** ⇒
⭐ **阶段 1/2 的新引擎也必须遵守这条契约**（原生只传/收字符串）⇒ 这次修的活不会白做。

## 8. ⭐⭐⭐ 阶段 1 原料盘点（2026-11-10 实测 ⇒ 风险比想象小得多）
轻阅**老引擎通路完好**，与新引擎 op 同级：
- `QiReaderLite/Resources/engine/engine.js`（2386 行）`OPS` =
  `ping search login loginProbe sourceHosts sourceVars filterAction exploreKinds explore explain explainToc bookInfo toc content`（13 个 op，**主链路全覆盖**）
- `QiReaderLite/Core/RuleSandbox.swift`（1559 行）宿主能力 22 个 case =
  `cacheFile cacheGet cachePut cacheRemove cacheText deviceID getCookie getString getStringArray getWebViewUA importScript log openBrowser ping readCache readFile removeCookie request setCookie showBrowser sourceHeader toast`
⇒ **全量替换不是「从零重写」，是「切回一条已验证过的成熟通路」** ⇒ 接线可以做成 **op 一一对应的对称替换** ⇒ 风险可控。
⇒ ⭐ 且阅读2.0 的架构（Swift 主体 + WKWebView 求值 + JS 取值层）**正是我们老引擎的形态**
⇒ ⇒ 「学人家」= **给已有老引擎按他的设计升级**（stage 诊断 / engineGen / stringRuleCache / debugObserver），
   **不是引入新技术** ⇒ 也就不必拷他的 ruleEngine.js 原文（版权干净）。

## 9. ⭐ 阶段 1 已落地（build287 · commit `ba007bc`）

### 改动
1. **新增 `QiReaderLite/Core/EngineMode.swift`**：引擎模式
   - `.webView`（**默认**）= WebView 引擎 = **阅读2.0 同款架构**（Swift 宿主 + WebView 内规则求值 + 原生只过字符串）
   - `.swiftEngine` = 自研 Swift 引擎（legado-engine）⇒ **保留作回退**
   - 开关：UserDefaults `qr.engine.mode` + **自检面板底部一键切**（换引擎不用出新包）
2. **`SourceService.invokeEngine` 按模式分流**；新增 `invokeWebViewEngine`
   - 走 `RuleSandbox.shared.invoke(op, payload, source:)` ⇒ 规则求值在 WebView 里做
     ⇒ 站方 JS 跑在**独立 WebContent 进程** ⇒ 对 jetsam 更友好 ⭐⭐⭐
   - ⭐ 老引擎把异常包成 `{error:…}` **返回**（不抛）⇒ 必须翻译成失败，否则会被当成成功
   - ⭐⭐⭐ 补 `__sourceVariableChanged`（**与灌进去的种子比较**）⇒ 「站方变量改没改」**不自证**
     （不自证 ⇒ 存量污染永远清不掉 ⇒ 真机 403 的老坑）
3. **门禁**：`op-routing-contract.test.js` **翻过来钉新契约**（旧版钉的是「主链路必须走新引擎」）
   + 新增 `engine-mode-switch.test.js`（含 7 种变异对照）
4. build 号 286 → 287

### 为什么接线这么便宜（实测结论）
- 老引擎 `OPS` = 13 个 op（ping/search/login/loginProbe/sourceHosts/sourceVars/filterAction/
  exploreKinds/explore/explain/explainToc/bookInfo/toc/content）⇒ **与新引擎 op 一一对应**
- 两条通路**返回契约一致**：search/explore `{books,total,nextUrl}` · exploreKinds `{kinds,filters}` ·
  bookInfo `{book}` · toc `{chapters}` · content `{content}` ⇒ App 的 DTO **不用改**
- `call()` 里**早就备齐**了老引擎要的一切：`__variables` / `__variable`（站方变量）/ `__loginInfo` /
  `__loginHeader` / `cookieSnapshot` ⇒ **payload 零改动**
