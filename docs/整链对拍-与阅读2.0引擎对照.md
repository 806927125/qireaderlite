# 整链对拍台（2026-11-18）—— 用「同输入」把两套引擎的差集变成待查清单

## 为什么要它
轻阅有两套引擎：① 自研 Swift 引擎（legado-engine）② 老 WebView 引擎（RuleSandbox + engine.js）
⇒ 「新引擎更强」这个说法**从来没有被逐 op 证明过** ⇒ ⭐ 用**同输入**对拍 ⇒ 差集 = 纯解析/求值差异。

## 台子怎么搭（可复现 / 不依赖网络 / 秒级）
1. **录真实响应**：`curl` 站方接口 ⇒ 存 fixture（例：`/legado/explore/menu` = 364 条分类，79KB）
2. **老引擎侧**：Node + `test/harness.js`（jsdom）+ `nativeMock` 按 URL path 匹配喂 fixture ⇒ 结果当 **oracle**
3. **Swift 引擎侧**：legado-engine 的 `SourceEngine` + `FixtureTransport`（HTTPTransport）+ **Node 后端**（Linux 可跑）
4. **逐项求差集** ⇒ **差集 = 待查清单**（不是「错误」！老引擎 ≠ 栖阅 ⇒ 差异里可能有一部分是老引擎对、栖阅错）

## 第一环实测（exploreKinds，NovelHub 聚合源）
| 项 | 值 |
|---|---|
| 老 WebView 引擎 | **439** 个 kinds |
| 自研 Swift 引擎 | **439** 个 kinds |
| **差集** | **0** ⭐⭐⭐ |

⇒ ⭐⭐⭐ **分类环两套引擎完全等价** ⇒ 「换引擎」的收益**不在分类**
⇒ ⇒ 真正的差异只可能在**详情 / 目录 / 正文**三环
⇒ ⇒ 而那三环正是聚合源最吃紧的：`@js:` 规则 + `data:;base64` 伪 URL（**老引擎特有**的处理）⭐⭐⭐

## 下一环（待做，已铺好模板）
- 详情：详情页 fixture（含 `data:` 载荷）⇒ 跑 `bookInfo` ⇒ 比书名/作者/简介/书链
- 目录：目录 fixture ⇒ 跑 `toc` ⇒ 比章节数/章名/章链
- 正文：章节 fixture ⇒ 跑 `content` ⇒ 比字数/首尾段
- ⚠️ `data:;base64` 载荷**不走 transport** ⇒ 录制器要能捕获它 ⇒ 别只录 HTTP

## 门禁口径
- 差集**只报告不硬断言**（老引擎不是栖阅 ⇒ 差异可能是「老引擎对、栖阅错」）⇒ 差集是待查清单 ⭐⭐⭐
- 只硬断言「两边不能都空」⇒ 防对拍台自己坏掉（假绿）
