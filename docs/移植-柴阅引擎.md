## ⭐⭐⭐ 本轮沉淀

1. ⭐⭐⭐ **SwiftPM 的 build plan（`.build/*.yaml`）不会自动纳入新加的 `.swift` 文件**
   ⇒ 新文件根本没被编译 ⇒ 报「cannot find X in scope」⇒ **看起来像代码写错，其实是 plan 过期（假红）**
   ⇒ 正解：编译前 `rm -f .build/*.yaml`（已固化进 `linux-compile-gate.sh`）⭐⭐⭐
2. ⭐⭐⭐ **Linux 沙盒编不到的代码 ⇒ 必须有静态门禁兜底**
   ⇒ 本轮真实事故：柴阅的 `Digests` 拆文件时漏了 `import CommonCrypto` ⇒ Linux 全绿 ⇒ CI 才报 ⭐⭐⭐
   ⇒ 正解：`conditional-import-gate`（用了某框架的符号 ⇒ 该文件必须 import 它）⭐⭐⭐
3. ⭐⭐⭐ **同一模块里「跨文件同名」不一定是撞名** ⇒ 若两份定义处于**互斥的条件编译**（`canImport(X)` vs `!canImport(X)`）⇒ 合法
   ⇒ 正解：门禁要豁免「条件互斥」的同名（否则会误报）⭐⭐⭐

## build304：修「发现页筛选键没用」（真机实证）

**症状**：用户在发现页选了「平台 = QQ阅读」⇒ **列表一点没变** ⇒ 筛选完全无效（不报错、不崩）。

### 根因（四个断点，全部静默）

| # | 断点 | 机制 |
|---|---|---|
| ① | **宿主没传 `infoMap`** | 站方 action 的真实形态：<br>`var m={"番茄":"番茄",…}; var v=infoMap["平台"];`<br>`var nv=(v!==null&&v!==undefined&&m[v]!==undefined)?m[v]:"默认";`<br>`c["find_source"]=nv; source.setVariable(JSON.stringify(c));`<br>⇒ **`infoMap` 拿不到值 ⇒ 站方回落到默认值 ⇒ 看起来完全没反应** |
| ② | **柴阅的 `exploreKinds` 命中缓存** | 缓存键 = md5(源URL + exploreUrl **文本**) ⇒ **站方变量变了键也不变** ⇒ 分类 URL 还是旧平台的 |
| ③ | **App 侧 `kindsCache`（30 分钟）不失效** | 它只读【**书源变量槽**】⇒ 而站方 action 写的是【**站方变量整串**】（`source.setVariable`）⇒ 看不到变化 |
| ④ | UI 侧 | ✔ 没问题（`loadKinds` 会重跑 `loadBooks`）|

### 修法

1. `SourceService.applySourceFilter` ⇒ `p["infoMap"] = [title: value]` ★核心
2. 宿主 `exploreKinds` op ⇒ `web.exploreKinds(refresh: true)`（柴阅默认 false ⇒ 命中旧缓存）
3. `kindsCacheKey` ⇒ **同时读站方变量槽**（对齐站方 jsLib 里写的约定：「轻阅的发现页缓存键 = bookSourceUrl|find_source|find_tab」）
4. 筛选成功 ⇒ `Self.invalidateKindsCache(source:)`（确定性失效，不依赖缓存键猜对）

### 门禁

`test/filter-action-wiring.test.js`（18 项 + 4 变异）：钉死四个断点 + **从真源 jsLib 取站方 action 的证据**（不靠推理）。

### ⭐ 复盘

⭐⭐⭐ **站方 action 的形态必须从真源 jsLib 里读**（我一度以为 `m` 是 `JSON.stringify` 后的字符串 ⇒ 判「站方 action 必然失效」⇒ **差点做出错误的修法**）⇒
**真正的证据是 `_dlhRow` 的定义**（`var m={"番茄":"番茄",…}` 是**对象字面量**）⇒ ⇒ 只差 `infoMap` 一个参数 ⇒ 修法简单且零风险。
⭐⭐⭐ 这正是「先证明原始输入真的坏，再下结论」的老纪律在**站方脚本**上的应用。

## build305：修「筛选键没用」**二次**（真正命中根因）

> ⚠️ **build304 没生效** ⇒ 诚实复盘：build304 只补了 `infoMap`，**但 UI 走的是另一条路** ⇒ 没触发。

### 站方 exploreUrl 的真实读法（真源 jsLib 原文）

```js
var NH_D = {"src":"全部","gender":"全部","status":"不限","sort":"最热","line":"自动"};
var _raw = String(source.getVariable()||"").trim();
if (_raw !== "") { var _o = JSON.parse(_raw); if (_o && typeof _o==="object") NH_D = _o; }
// ……
if (typeof infoMap !== "undefined" && infoMap && typeof _NH_PLAT !== "undefined") {
    var _sw = String(source.get("nhPlatSwitch")||"");
    if (_sw !== "" && …) { /* 菜单切台：以源变量为准 */ }
    else { var _imv = String(infoMap["平台"]||"");        // ← 「下拉框说了算」
           if (_imv!=="" && _NH_PLAT.indexOf(_imv)>=0 && String(NH_D.src)!==_imv) {
               NH_D.src = _imv; source.setVariable(JSON.stringify(NH_D)); } }
}
```

⇒ ⭐⭐⭐ **站方读的是【站方变量整串】里的 `src`** ⇒ 而轻阅抠出的 paramKey 是 **`find_source`** ⇒ **键名对不上 ⇒ 站方根本不读** ⭐⭐⭐

### 为什么 build304 没用

- UI 的分流：`paramKey` 非空 ⇒ 走「**① 轻阅自己写源级变量**」⇒ **站方 action 根本没执行** ⇒ 我补的 `infoMap` 从未被触发 ⭐⭐⭐
- 而 ① 这条路用 `setHostMap` **整份覆盖**站方变量槽 ⇒ 把站方的 `src`/`gender`/`status` **全冲掉** ⭐⭐⭐

### 修法（**全在 Core，UI 零改动**）

1. `SourceVariables.setHostMap` ⇒ 站方变量改成**增量合并**（保留站方自己的键）⭐⭐⭐
2. ⇒ **站方约定同步**：`find_source` ⇒ `src`（真源 jsLib：`c['src']=v; c['find_source']=String(v);` ⇒ 同值两键名）⭐⭐⭐
3. build304 的三处保留：`infoMap` 传参（② 路径）、`exploreKinds(refresh: true)`、`kindsCacheKey` 读站方变量槽 + 筛选后清缓存 ⭐⭐⭐

⇒ **无 `infoMap` 时站方 exploreUrl 会保留 `NH_D.src`** ⇒ 轻阅写进去的平台**立即生效** ⇒ 分类按新平台生成 ⭐⭐⭐

### 门禁（这一轮的关键升级）

`test/filter-var-roundtrip.test.js` + `test/filter-var-roundtrip.swift`：
⭐⭐⭐ **用 `swiftc` 编 App 的真文件真跑「写入 → 站方读回」**（不是静态断言）⇒
· 断言站方读到的 `src` = 新平台 ✔
· 断言站方的 `gender`/`status`/`sort`/`line` **没被冲掉** ✔
· **2 个真变异**（改回整份覆盖 / 去掉 src 同步）⇒ 真跑必须失败 ✔（门禁有牙齿）
· 证据直接取自**真源 jsLib**（不靠推理）⭐⭐⭐

### ⭐⭐⭐ 本轮复盘（跨项目通用）

1. ⭐⭐⭐ **「补一个参数」不等于「链路通了」** ⇒ 必须问「**这条路上还有别的分支吗**」⭐⭐⭐
   （build304 补了 `infoMap`，但 UI 有**两条分流**，另一条压根不经过它）⭐⭐⭐
2. ⭐⭐⭐ **静默失效类问题，必须用【真跑】的门禁，而不是「代码里写了某个键」的静态断言** ⭐⭐⭐
   ⇒ 静态断言只能证明「我写了」，不能证明「对方读的是这一格」⭐⭐⭐
3. ⭐⭐⭐ **读对方的真实读法（从真源 jsLib 里抄原文），别读自己以为的读法** ⭐⭐⭐

## build307：把筛选键做成【通用】（用户：「筛选键我要通用啊，大灰狼不行」）

### build305 的错误（诚实复盘）

build305 我为了修 NovelHub，**硬编码了「`find_source` ⇒ 同步 `src`」** ⇒ ⇒ **只对 NovelHub 有效** ⇒ **大灰狼被带坏了** ⇒ ⇒ 用户直接指出「我要通用」⭐⭐⭐

### 通用解（三条，缺一不可）

1. ⭐⭐⭐⭐⭐ **优先【执行站方 action】**（站方自己知道该写哪个键 ⇒ 天然通用；栖阅/柴阅都这么做）
   · 🍒NovelHub：`c['src']=v; c['find_source']=String(v); c['find_tab']='小说';` ⇒ 站方写 **src** ⭐⭐⭐
   · 🍅大灰狼：`show(infoMap['平台'],'find_source')` ⇒ 站方写 **find_source** ⭐⭐⭐
   ⇒ **宿主不猜键名** ⇒ 一个源也不写死 ⇒ **通用** ⭐⭐⭐
2. ⭐⭐⭐ **action 失败 ⇒ 兜底「轻阅自己写」**，且**键名从 action 里解析**：
   · `ExploreKindsNormalizer.filterAssignedKeys(in:)`（**两步判据**）⭐⭐⭐
     ① 找出「由 infoMap 派生」的变量（`var v=infoMap['平台']`）⭐⭐⭐
     ② 找出「赋值右侧引用了它」的键（`c['src']=v` ✔ / `c['find_source']=String(v)` ✔ / `c['find_tab']='小说'` ✘ 固定值）⭐⭐⭐
   · 解析不出 ⇒ 退回 `paramKey`（大灰狼的 `find_source`）⭐⭐⭐
3. ⭐⭐⭐ **站方变量槽只写「用户刚改的那几项」**（增量合并）⇒ 站方自己的 `gender`/`status`/`sort` 原样保留 ⭐⭐⭐
   ⇒ ⚠️ **绝不把整份 map 合并进去**（那份含**站方默认表**⇒ 会把站方状态重置成默认值）⭐⭐⭐

### 验证（真跑，两个源形态都验）

`test/filter-var-roundtrip.swift`（用 `swiftc` 编 **App 的真文件**）：
· **场景 1（NovelHub）**：action 里解析出 `["src","find_source"]`（**不含**固定值的 `find_tab`）⇒ 站方读到 `src` = 新平台 ⇒ 且 `gender`/`status`/`sort` 保留 ⭐⭐⭐
· **场景 2（大灰狼）**：action 里解析不出 `c['k']` ⇒ 退回 `paramKey` ⇒ 站方读到 `find_source` = 新值 ⇒ 且 `gender` 保留 ⭐⭐⭐
· **3 个真变异**（整份覆盖 / 不用 stationKeys / 再一处整份覆盖）⇒ 真跑必须失败 ⇒ 门禁有牙齿 ⭐⭐⭐

门禁 `filter-action-wiring` 加了「通用性」断言 + 2 个变异（不优先 action / 硬编码 `src`）。

### ⭐⭐⭐ 复盘（跨项目通用）

⭐⭐⭐ **「修好一个源」不等于「修好了这类问题」** ⇒ 每修一个源都要问：**下一个源的形态会不一样 ⇒ 我的修法还成立吗** ⭐⭐⭐
⭐⭐⭐ **正确做法：让【对方】写（执行站方 action）而不是【我】猜键名** ⭐⭐⭐
